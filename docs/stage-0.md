# Этап 0 — детализация ТЗ v0.2

Дата: 30.10.2026. Документ фиксирует результаты этапа 0 (архитектурные решения,
машинные схемы, макеты, эталонные данные, политика версии Home Assistant) и
честно перечисляет, что из P0 уже реализовано, а что осталось.

## 1. Границы и принципы

1. Ядро не импортирует Home Assistant и тестируется обычным `pytest`.
2. Интеграция HA — тонкий адаптер: снимок состояния, история, доставка, UI.
3. Никакого исполнения пользовательского кода и шаблонов: только JSON-AST.
4. Неизвестное состояние никогда не приравнивается к норме автоматически.
5. Числа, пороги и факты формируются локально; модель только объясняет.
6. Версия 1.0 — только чтение (`SEC-01`).

## 2. Архитектурные решения (ADR)

### ADR-01. Разделение «ядро / адаптер»

*Контекст:* правила, таймеры и инциденты должны проверяться без поднятого HA,
а HA-специфика не должна протекать в предметную логику.

*Решение:* `core/` — чистый Python (единицы, модель, правила, вычислитель,
инциденты, история, ИИ, отчёты, уведомления, хранилище). `coordinator.py`,
`history_provider.py`, `provider.py`, `sensor.py`, `panel.py` — адаптеры.

*Следствия:* быстрые unit-тесты (88 шт. без HA), простая замена источника истории
(P2 InfluxDB), но требуется явная передача времени и снимков в ядро.

### ADR-02. Трёхзначная логика и политика отсутствующих данных

*Решение:* результат условия — `true | false | unknown`. Политика правила
(`RULE-06`): `unknown` (по умолчанию, тревоги нет), `ignore` (неизвестные
под-условия отбрасываются; если не осталось известных — снова `unknown`),
`treat_as_failure` (неизвестное считается срабатыванием), `separate_data_quality_incident`
(событие качества данных без инцидента аварии).

*Следствия:* «тихий» датчик не даёт ложной аварии и не маскирует отказ; поведение
правила однозначно и покрыто тестами `test_missing_data_policies`,
`test_ignore_policy_combines_known_values`.

### ADR-03. JSON-AST вместо кода и шаблонов

*Решение:* `core/rules.py` разбирает дерево `all/any/not` и атомарные проверки,
проверяет глубину (8), число узлов (200), существование измерений, совместимость
единиц и типов. `duration_true` допустим только прямым потомком корневого `all`
(иначе — `for_seconds`). Неизвестные поля отклоняются, а не игнорируются.

*Следствия:* опечатка в правиле не «сохраняется молча»; сравнение °C и V невозможно;
схема зафиксирована в `docs/schemas/rule.schema.json` и проверяется тестами.

### ADR-04. История: предзагрузка в executor, никаких выдуманных трендов

*Решение:* координатор перед оценкой собирает нужные окна через
`recorder.history.state_changes_during_period` в executor и передаёт ядру
`CachedHistory`. `delta_above`/`rate_above` при недостаточном покрытии дают
`unknown` + причину `history_missing`. Отчёт печатает покрытие и «нет данных»,
а не «всё стабильно» (`HIST-02`, `AC-10`).

Уточнения 0.3.1: история читается по атрибуту измерения (для `climate` —
`current_temperature`, а не режим), покрытие системы считается как среднее по
датчикам (максимум одного источника не выдаётся за всю систему), а для счётчиков
энергии прирост учитывает сбросы. Обязательные показатели профиля не отсекаются
лимитом компактного отчёта.

Уточнения 0.3.3: ожидание Recorder и чтение истории ограничены настраиваемым
таймаутом (по умолчанию 5 с), по таймауту отчёт формируется по текущим показаниям
с явной пометкой, а быстрые правила историю не ждут. Кэш отчёта ключуется профилем,
эффективным режимом ИИ и ревизией настроек, поэтому смена `use_ai` или правка
профиля не возвращает старый текст.

### ADR-05. Контракт ИИ с фактами и fallback

*Решение:* пакет (`docs/schemas/ai-package.schema.json`) содержит только
разрешённые поля; у каждого вычисленного отклонения есть `id`. Ответ проверяется
схемой, ссылки `evidence_refs` обязаны разрешаться, `attention_level` не может
понизить локальную критичность, неподтверждённые числа помечаются, а не удаляются
молча. Любая ошибка (сеть, 401/402/429/5xx, битый JSON, пустой ответ) приводит к
шаблонному отчёту с локальными фактами (`AI-03`, `AI-07`, `NFR-04`, `AC-11`, `AC-12`).

### ADR-06. Хранение и миграции

*Решение:* один `Store` с `schema_version=1`; миграция `0 → 1` (payload без версии)
с резервной копией; повреждённый JSON — `StorageError`, а не «починка» наугад;
экспорт вырезает ключи `api_key|token|password|secret|bot_token` (`STO-01…STO-04`, `CFG-06`).

### ADR-07. Время

*Решение:* ядро работает в UTC, отображение — в часовом поясе HA
(`zoneinfo`); `ensure_utc` приводит наивные метки к UTC. Таймеры правил после
рестарта пересчитываются из UTC-времени; неизвестное состояние не имитирует
непрерывные измерения (`DATA-04`, `INC-05`).

### ADR-08. Read-only и защита от prompt injection

*Решение:* в 1.0 нет вызовов `hass.services.async_call` для управления
устройствами; тексты сущностей — данные; системные инструкции неизменяемы;
`evidence_refs` и локальные цифры обязательны (`SEC-01…SEC-04`, `AI-05`).

### ADR-09. Минимальная версия Home Assistant

*Проблема:* ТЗ запрещает декларировать неподтверждённую минимальную версию.

*Решение на этапе 0:* версия **не заявлена** — в `hacs.json` нет ключа
`homeassistant`, в `manifest.json` нет версии HA. Целевая политика: актуальный
стабильный HA на дату выпуска и две предыдущие месячные версии. Минимальная
версия фиксируется в `hacs.json` и README только после зелёного прогона CI на
этой версии (этап 1).

*Проверяемые API:* Config Flow, `panel_custom`, `StaticPathConfig`,
`state_changed`, `recorder.history.state_changes_during_period`,
`websocket_api`. Все обращения к Recorder обёрнуты в обработку отказа.

### ADR-10. Разделение тестовых контуров

*Решение:* `tests/` — ядро и контракты (без HA, секунды); `tests/ha/` —
интеграция через `pytest-homeassistant-custom-component`. CI: lint, типы,
unit, контракты, HA-тесты, проверка переводов и manifest.

| Ответ ИИ | [schemas/ai-response.schema.json](schemas/ai-response.schema.json) | [fixtures/ai_response_example.json](fixtures/ai_response_example.json) | `tests/test_schemas.py`, `core.ai.validate_response` |
| Хранимая конфигурация | [schemas/configuration.schema.json](schemas/configuration.schema.json) | собирается из модели и правила | `tests/test_schemas.py`, `core.storage.validate_state` |
| Модель дома | — (dataclass-контракт) | [fixtures/home_model_example.json](fixtures/home_model_example.json) | `HomeModel.from_dict`, round-trip тест |

Примечания:

* `notify` — допустимый входной alias (`repeat_seconds`, `on_recovery`), каноническая
  форма хранения — верхнеуровневые поля правила.
* `duration_true` внутри `any`/`not` или `for_seconds` + `duration_true` одновременно —
  ошибка схемы (проверяется и JSON Schema, и парсером).
* Пороги в примерах **условные** и не являются рекомендациями по электробезопасности.

## 6. Трассировка требований

| Блок ТЗ | Реализовано в ядре / адаптере | Покрыто тестами | Осталось |
|---|---|---|---|
| CFG-01…06 | `config_flow.py`, `storage.py` | миграции, экспорт без секретов | UI групп/правил/расписаний, откат версии конфигурации |
| ENT-01…04 | `entity_catalog.py`, `core/discovery.py`, `model.py` | подсказки, фильтры, канонический источник, `broken_sources` | восстановление разорванной связи в UI |
| SEM-01…07 | `model.py` | циклы, роли, составные источники, единицы | граф в UI |
| DATA-01…06 | `observations.py`, `units.py` | качество, `last_reported`, конверсии | статистика качества по окнам |
| RULE-01…10 | `rules.py`, `engine.py` | AST, длительность, гистерезис, cooldown, политики | симулятор на истории (P1), конструктор в UI |
| INC-01…07 | `incidents.py`, `notifications.py` | дедуп, ACK, восстановление, очередь, рестарт | кнопки Telegram, эскалация по расписанию |
| HIST-01…08 | `history.py`, `history_provider.py` | покрытие, сбросы счётчика, энергия, «нет тренда» | long-term statistics, сравнения/аномалии (P1), InfluxDB (P2) |
| AI-01…10 | `ai.py`, `provider.py` | схема, `evidence_refs`, floor критичности, коды ошибок | бюджеты токенов/денег, кэш слепков, read-only tools (P2) |
| REP-01…07 | `reports.py`, координатор | адаптивная детализация, факты vs ИИ, fallback, разброс фаз | расписания и профили в UI |
| TG-01…07 | отправка через `notify`, постоянные уведомления | очередь, тихие часы, подавление | команды `/status`, `/report`, ACK-кнопки, allowlist |
| UI-01…07 | Config/Options Flow, панель, WebSocket, сервисы | каталог, редактор систем/датчиков/правил, профили, ACK | вложенные условия, промпты, полная локализация панели |
| STO-01…04 | `storage.py`, `Store` | миграции, порча JSON, экспорт | ротация журнала по количеству |
| SEC-01…06 | валидация ядра, провайдер | отсутствие eval, разрешённые схемы | `ActionGateway` (P3) |
| NFR-01…06 | executor-история, retry-политика, диагностические сущности | классификация статусов | нагрузочный профиль 500 сущностей / 300 правил |

## 7. Проверка

```bash
python -m pytest tests -q            # ядро и контракты, HA не нужен
python -m pytest tests/ha -q         # интеграция HA (pytest-homeassistant-custom-component)
```
